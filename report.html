Phase 1: Object Storage Foundation

Implementation Summary

object_write builds the full object by prepending a type header (blob <size>\0, tree <size>\0, or commit <size>\0) to the raw data, computes a SHA-256 hash over the combined bytes, shards the path by the first two hex characters of the hash, and writes atomically using a temporary file followed by rename. object_read reads the stored file, recomputes the hash to verify integrity, parses the header to extract the object type and data size, and returns the data portion after the null byte.

Phase 2: Tree Objects

Implementation Summary

tree_from_index walks the index entries and builds a recursive directory hierarchy. Files at the root go directly into the root tree. Files under subdirectories (e.g. src/main.c) are grouped by their first path component, and write_tree_level is called recursively to produce a subtree object. Each tree entry contains the file mode, the SHA-256 hash of the blob or subtree, and the name. All entries are sorted before serialization to guarantee deterministic output.

Phase 3: The Index (Staging Area)

Implementation Summary

index_load opens .pes/index and parses each line in the format <mode> <hash-hex> <mtime> <size> <path>, populating an Index struct. A missing index file is treated as an empty index, not an error. index_save sorts entries by path and writes to the index file. index_add reads the target file, calls object_write to store the blob, captures mtime and size via stat, and either updates an existing entry or appends a new one.

Implementation Summary

It then calls head_read to get the parent commit hash (absent on the first commit), builds the commit text, calls object_write to store it, and calls head_update to atomically advance the branch pointer to the new commit hash.

Phase 5: Branching and Checkout (Analysis)

Q5.1 — Implementing pes checkout <branch>

A branch is a file at .pes/refs/heads/<branch> containing a commit hash. To implement checkout: read the target branch file to get its commit hash and follow it to its tree object; update .pes/HEAD to contain ref: refs/heads/<branch>; then reconstruct the working directory by walking the tree recursively — writing each blob's contents to the corresponding path, creating intermediate directories as needed, and deleting files that exist in the current tree but not the target.

What makes this complex is protecting uncommitted user work. A correct implementation must compare the target tree against the current HEAD tree and index to identify which files actually differ, and only touch those. Any file modified in the working directory but not staged — that also differs between branches — is a conflict that must abort the checkout.

Q5.2 — Detecting Dirty Working Directory Conflicts

The algorithm uses three sources: the current HEAD tree, the index, and the working directory on disk. For each file in the target branch's tree, hash its current on-disk contents and compare against the index hash and the HEAD tree hash. A conflict exists when all three differ — the file has been modified, the modification is unstaged, and the target branch has a different version. If the working directory hash matches the index hash (file is clean), or the file does not exist in the target tree, the operation is safe.

Q5.3 — Detached HEAD

In detached HEAD state, .pes/HEAD contains a raw commit hash. New commits are stored and HEAD is updated to each new hash, but no branch pointer is updated — the chain is only reachable via HEAD itself. If the user runs pes checkout <branch>, HEAD is overwritten and the detached commits become unreachable. Recovery requires knowing the commit hash — the user can write it to a new file in .pes/refs/heads/. Without the hash, recovery is only possible if a reflog was maintained.

Phase 6: Garbage Collection (Analysis)

Q6.1 — Finding and Deleting Unreachable Objects

The algorithm is mark-and-sweep using a hash set of reachable object IDs. The marking phase reads every file under .pes/refs/ plus HEAD to collect all branch tip hashes, then recursively traverses every commit's tree and parent chain, adding all blob and subtree hashes to the reachable set. The sweep phase enumerates every file under .pes/objects/ and deletes any whose hash is absent from the set.

For 100,000 commits and 50 branches, assuming ~12 objects per commit (commit + tree + ~10 blobs), total objects ≈ 1.2 million. The marking phase visits each reachable object once — O(n) hash set insertions. The sweep phase is one directory listing pass. Both phases are O(n) in total object count.

Q6.2 — GC Race Condition with Concurrent Commits

A commit writes blob and tree objects first, then updates the branch reference. If GC runs its mark phase between these two steps — after new objects exist but before the branch pointer is updated — those objects are not reachable from any reference and will be swept. When the commit then writes the commit object referencing those blobs, they are gone and the repository is corrupted.

Git avoids this with two mechanisms: a grace period (GC never deletes any object modified within the last two weeks, regardless of reachability), and mtime-based exemption for loose objects (newly created loose objects are exempt from collection even if not yet referenced). Together these ensure objects created during an ongoing commit survive until the commit finalizes.
